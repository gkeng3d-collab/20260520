## C. ประเด็นที่ตกลง "จดไว้ใน MoM — ไม่ต้องแก้ Blueprint"

1. **ค่า pending ของ EPPO ที่เก็บเป็น 0** (27:32–30:48) — ค่าที่ยังไม่ประกาศ ระบบเก็บเป็น 0; manager กังวลว่า user จะเข้าใจผิดว่าเป็นค่าจริง อยากให้แสดงเป็น dash/blank แทน → มี 2 แนวทาง: (ก) format ที่ชั้น report ให้ 0 แสดงเป็นว่าง หรือ (ข) ไม่นำค่าเข้าจนกว่าจะประกาศ (เป็น blank จริง) → **ตกลงจดเป็นประเด็นใน MoM แล้วตัดสินใจตอนเริ่มเก็บข้อมูลจริง โดย R2 จะ demo ผลการแสดงให้ดูก่อน** (ฝั่ง TOP เสนอเองว่าไม่ต้องแก้ Blueprint จะได้ไม่แก้เยอะ)
2. **Exchange rate ในตารางโครงสร้างราคา EPPO** (~28:00) — ไม่ได้ระบุใน BBP ฉบับนี้เพราะส่วนบนของตารางทำไว้แล้วในระบบเดิม (เก็บอยู่แล้ว) — รับทราบร่วมกัน
3. **ตัวกำกับ Yearly / Monthly / Month-to-date** (35:24–37:19) — ตาราง (CMA?) ที่มีหลายมิติเวลา มีฟิลด์กำกับใน data model อยู่แล้ว พร้อม date key — จิดารินเปิดตัวอย่าง data model ให้ดู เข้าใจตรงกัน ไม่แก้เอกสาร
4. **Master data mapping เมื่อชื่อสินค้าเปลี่ยน** (~1:05) — เช่น เอทานอล/สารเติมแต่ง เปลี่ยนชื่อข้ามเดือน → รองรับด้วย process DOEB master data validation (BW ตรวจ → iRPA แจ้งทีมทาง email → ทีม maintain ผ่าน Excel → iRPA โหลดกลับเข้า BW → data hub/report อัปเดต)

## D. ข้อตกลงเรื่องกระบวนการทำงานร่วมกัน

1. **ส่งเอกสารก่อนประชุมล่วงหน้า** — TOP ขอรับเอกสารก่อน meeting เพื่อให้ทีม+manager รีวิวก่อน (บางรอบเข้าไม่ครบ ตัดสินใจในห้องไม่ได้) → R2 ตกลง: ประชุม weekly วันพฤหัส จะส่งเอกสารราวพุธเช้า
2. **Weekly meeting 1 ชม./สัปดาห์** หลัง BBP confirm ไปจนถึงช่วง UAT — อัปเดต progress/timeline, ปิดประเด็น; การตัดสินใจที่ตอบในห้องไม่ได้จะบันทึกใน MoM พร้อมกำหนดขอคำตอบ (ราวก่อนประชุมครั้งถัดไป)
3. **เรื่องด่วน** ใช้แชทกลุ่มขอ confirm/solution ได้เลย ไม่ต้องรอรอบประชุม / ฝั่ง TOP ขอให้ระบุชัดว่าประเด็นไหนต้องการคำตอบภายในเมื่อไร
4. **ช่วง develop** — R2 จะโชว์หน้าตา data hub ในรอบ weekly และ export ไฟล์ส่งให้ TOP นั่งรีวิวได้ (เช่น ตรวจชื่อหัวตารางอย่าง Document Date อีกรอบ)
5. **เงื่อนไขการขึ้นระบบ** — Dev → QAS → Production: จะเอาของขึ้น test ที่ QAS ได้ต้องมี user confirm Blueprint (email) ก่อน
